# PROJECT KNOWLEDGE BASE

Detailed conventions: [docs/coding-conventions/README.md](docs/coding-conventions/README.md).

## OVERVIEW
Discord bot + archive worker + CLI in one TypeScript package. Core domains are Discord event handling, icon replacement/search, LLM summarization/QA, embedding pipelines, and optional Kafka fan-out.

## STRUCTURE
```text
./
|- src/                    # runtime code (see src/AGENTS.md)
|  |- index.ts             # main bot runtime
|  |- archive.ts           # archive runtime
|  |- cli.ts               # ops CLI entrypoint
|  |- deploy-commands.ts   # slash command registration tool
|  |- controller/          # Discord event entrypoints
|  |- service/             # application workflows
|  |- repository/          # data/provider adapters
|  |- database/            # mongoose connection + schemas
|  \- utils/               # shared helpers + AI/provider integration
|- static/                 # prompt sources fetched from GitHub at runtime
|- docs/coding-conventions/ # evidence-backed module conventions + black-box comparisons
|- docs/readme.md          # local bootstrap notes
|- scripts/                # docker helper scripts
\- .github/workflows/      # develop->main PR automation
```

## CONVENTIONS
- Runtime env naming is `prod`/`dev` (not `production`/`development`); config picks `.env` for prod, `.env.dev` otherwise.
- Toolchain pins Node 24.x; `package.json` declares `packageManager: yarn@4.12.0`.
- TypeScript build is CommonJS, strict mode, emits declarations and strips comments.
- `cmd-prod` still runs TS source via `tsx` (`src/deploy-commands.ts`) instead of `dist/*`.
- CI workflow only automates PR creation from `develop` to `main`; there is no build/lint/test quality gate in Actions.
- Follow the detailed conventions in `docs/coding-conventions/`. Distinguish current contracts from known defects; do not copy defects as recommended patterns.
- Convention updates require three steps: inspect the feature/module; request an independent black-box implementation from a separate stateless LLM without source/internal conventions; compare with current code and document genuine mismatches as repo-incompatible examples. Never apply generated implementations as part of documentation work.
- CLI `--help` has import-time file logger and SQLite initialization. For non-mutating checks, use an isolated temporary source copy/work directory with dummy API settings.
- `config.ts` is the current environment contract; `src/global.d.ts` contains legacy provider keys and is not a complete current config map.

## ANTI-PATTERNS (THIS PROJECT)
- Do not edit `yarn.lock` manually (`DO NOT EDIT THIS FILE DIRECTLY`).
- Do not copy raw conversation text into QA/summarization outputs (`static/prompt-question.txt`).
- Do not include usernames/person-identifying names in generated summaries (`static/prompt-question.txt`, `static/prompt-summarization.txt`). Inputs may contain names; output anonymization is a separate policy.
- Do not add intro/outro boilerplate like "This image/content is ..." in embedding preprocess outputs (`src/service/embedding/client.ts`).
- Do not drop sensitive/uncomfortable source wording semantics during summarization (`static/prompt-question.txt`).

## UNIQUE STYLES
- Multi-runtime single package: main bot, archive worker, CLI, and command deploy tool coexist.
- Slash commands are plugin-like files loaded dynamically from `src/service/commands/`.
- Korean-first UX text for command descriptions and AI-facing output policy.
- Optional Kafka publishing is feature-gated by config (`KAFKA_ENABLE`, `KAFKA_REST_PROXY`).

## COMMANDS
Runtime commands are declared in `package.json`; this is a map, not permission to execute them.

| Purpose | Command | Execution constraints |
|---|---|---|
| Type check without emit | `yarn exec tsc --noEmit --incremental false` | Does not log in or touch runtime DBs |
| Build | `yarn build` | Emits `dist/`; uses `tsconfig.json` |
| Lint | `yarn lint` | Existing ESLint rules; `lint:format` means ESLint `--fix`, not Prettier |
| CLI | `yarn cli --help` | Import-time logger/SQLite side effects; isolate for read-only investigation |
| Bot | `yarn dev`, `yarn start` | NEVER RUN |
| Archive | `yarn archive-dev`, `yarn archive-start` | NEVER RUN |
| Command deployment | `yarn cmd-dev`, `yarn cmd-prod` | NEVER RUN; deletes global commands before registration |
| Docker helpers | `scripts/docker-up.sh`, `scripts/docker-register-commands.sh` | Destructive/runtime operations, not validation commands |

## NOTES
- No project test command is defined; no test framework config was found.
- `yarn build` runs `tsc` with `tsconfig.json`; `tsconfig.build.json` exists but is not wired by scripts.
- `scripts/docker-up.sh` force-removes/stops compose containers before recreate (no explicit volume removal flag).
- For subsystem details, start at `src/AGENTS.md` and drill down to child AGENTS files.
- Detailed convention ownership: Discord/commands/payloads; archive/persistence/embedding; AI/prompts; and core/runtime/adapters are indexed in `docs/coding-conventions/README.md`.
- Docker Compose runs bot and archive separately, mounts logs only, and does not provide Mongo/Elastic/AI services or a persistent SQLite database volume.
- DO NOT RUN `yarn dev`, `yarn start`, `yarn archive-dev`, `yarn archive-start`, `yarn cmd-dev`, `yarn cmd-prod` IN ANY CIRCUMSTANCE
